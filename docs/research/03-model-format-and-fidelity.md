# 03 - Sample model format and fidelity (T22a)

Date: 2026-10-12. All web pages accessed 2026-10-12. Local source checks were made against the
raylib 6.0 / cgltf 1.15 sources that CMake fetched into `build/clang-release/_deps/raylib-src`
(the exact code the viewer links), which is a primary source.

## 1. Recommendation in one paragraph

Store the models as **binary glTF 2.0 (`.glb`)**, generated by `tools/models/make_models.py`.
**Do not commit `.blend` files**: the script is the source, and a `.blend` is a version-specific
binary that cannot be diffed and duplicates it. Axes and units: metres, +Y up / +Z front in the
file (the Blender exporter default; modelled with the nose towards Blender -Y). Origin = the
entity reference point; every moving part is its own named node whose origin is its hinge.
Materials: glTF metallic-roughness base-colour factors, plus a `COLOR_0` vertex colour that
carries cheap baked shading and markings. **Fidelity level: "medium, geometry plus vertex
colour"**: bevelled and smooth-shaded shapes with real detail in silhouette and part breaks,
about 3-10 k triangles, no textures, no LODs. File budget: 40-120 KB per model, hard limit
200 KB. Reasons are in sections 3-4.

Sources for the table and notes:

* glTF coordinate system and node names: the Khronos glTF 2.0 spec states a right-handed system

* Unreal: the glTF support page lists `.gltf` and `.glb` and the exporter extensions

## 3. How articulated-part pivots survive

CIGI ICD 3.3 section 4.1.6 moves a part by an offset and an attitude; sections 3.4.2/3.4.3 define
the body and part frames. In glTF the only pivot a node has is the origin of its local frame, so
each moving part is a **node whose origin is the hinge**, with its mesh positioned around it.
Fixed neighbours are siblings, not parents, so rotating one part cannot disturb another; the only
deliberate parent/child pair is `barrel` under `turret` (the barrel follows the turret yaw).

* **raylib `LoadModel` (stock path)**: the comment above `LoadGLTF` in `rmodels.c` says
  transforms, including parent-child relations, "are applied on the mesh data, but the hierarchy
  is not kept". Node names are not retained and pivots are baked away. T22 must therefore use the
  vendored cgltf (MIT, version 1.15, `src/external/cgltf.h`, licence confirmed in its header)
  directly and compose `rest_transform * part_transform` per node. Our files suit that: one mesh
  per node, translation-only node transforms, unique names.
* **Index limit**: raylib truncates indices to `u16` ("Indices: u16, u32 (truncated to u16)"), so a
  single glTF primitive must have fewer than 65 536 vertices. T22 should warn on larger ones.
* **Not supported by raylib's loader**: Draco ("Draco compression not supported"), non-float
  positions/normals/texcoords, PBR specular-glossiness, scenes (all nodes are used). We use none
  of these.
* **Unreal** (to verify in T28): glTF nodes become components under Import Into Level, with each
  node's local origin kept as the component pivot. If not, USD is the fallback format.

Conventions fixed for all four models (enforced in the script):

* Unique lowercase snake_case node names, as in the T22a brief; `_l` / `_r` = left / right of the
  vehicle looking forward.
* Handedness: glTF has +Z front and +Y up, so the vehicle's right is -X (spec: "-X right"); a
  vehicle's left part therefore sits at +X. The existing `jet.glb` has `aileron_r` at +X, i.e.
  on the vehicle's left: this is a bug to fix in Phase 2 (swap the `_l`/`_r` sides).
* Origin: aircraft at the centre of gravity; ground vehicles at the centre of the ground contact
  patch (so the CIGI entity reference point sits on the ground).
* Hierarchy: one root (the body node: `fuselage`, `hull`, `cab`, ...). Fixed detail parts are
  extra children of it; moving parts are children of the root at their hinge, except `barrel`
  under `turret`.
* Hinge axes: control surfaces hinge along the body y axis (part pitch), rudder along the body z
  axis (part yaw), turret about the vertical (part yaw), barrel about the trunnion y axis (part
  pitch), rotors about the mast axis, wheels about their axle. `gear` is a single node used as a
  visibility component (state 0 hides it).

## 4. Fidelity: what is worth doing

What the viewer can show. In `apps/ig_viewer/renderer.cpp` the viewer's GLSL 330 shader computes
`vertexColor.rgb * colDiffuse.rgb * (ambient * skyfactor + sun * max(dot(n, sunDir), 0))` plus
fog. So **per-vertex normals and vertex colour matter; textures, normal maps, metallic-roughness,
occlusion and emissive are not sampled** (raylib's `LoadGLTF` reads them into material maps, but a
shader has to use them). With one sun and Lambert shading, silhouette, crease angles and large
shading gradients carry the realism, not surface detail. Details smaller than about 20 cm are
invisible at chase-camera distances.

| Technique | Visible in this viewer? | Script-reliable? | Cost | Decision |
|---|---|---|---|---|
| Bevels / rounded edges | Yes, catch the sun | Yes (bmesh, deterministic) | more tris | **Do**, 1-2 segments, large parts only |
| Smooth normals with crease angle | Yes, the biggest single win on fuselages, barrels, wheels | Yes | none | **Do** |
| More parts (doors, hatches, intakes, exhausts, hubs, road wheels) | Yes, makes the shape recognisable | Yes | more tris | **Do**, within the budget below |
| PBR values per material | Not in viewer shader; yes in Unreal | Yes | trivial | **Do** (honest roughness/metallic for T28) |
| Vertex-colour shading ("fake AO": darker undersides and cavities) | **Yes** | Yes: computed from normal and height, no baking | 4 B/vertex | **Do**, mild (0.55 to 1.0) |
| Baked AO via Cycles | Same visual | Poor: slow, sampling noise, determinism not guaranteed | - | Reject |
| Textures (livery, panel lines, camo) | Not sampled by the viewer today | Needs baking to PNG; determinism risk | 20-200 KB each | **Defer** |
| Markings (stripes, roundels) | Yes if geometry or vertex colour | Yes, as vertex-colour regions or thin quads | small | **Do** (simple stripes/insignia) |
| Emissive lights | Not in shader | Material only | none | Skip |
| LODs | Not used by the viewer; Unreal makes its own | Doable | x2-3 size | **Skip** (glTF has no portable LOD standard the importers read) |
| Transparent canopy | Possible, but sorting issues | Yes | none | Use a dark opaque tinted canopy |
| Skins / animation | Unsupported by T22 | - | - | Never |

Budgets and limits:

* Per model: 3 000-10 000 triangles, 6-14 nodes, at most 6 materials; file 40-120 KB `.glb`;
  hard limit 200 KB (the brief's default stands). The T22 acceptance is 200 entities at >= 60 fps;
  200 x 10 k triangles of Lambert shading is trivial for a GPU, while draw calls (nodes x
  materials) are the real cost, hence the node and material caps.
* No Draco/Meshopt: raylib cannot decode them, so size is controlled by the geometry budget.
* Preview PNGs <= 300 KB each.

Reliable in a script: primitives, lofts, extrusions, mirroring, bevel, smooth-by-angle, vertex
colour from geometry. Fragile: Cycles bakes, booleans on curved surfaces, texture decals,
anything with a threaded solver. Determinism: bmesh operations are deterministic and the glTF
exporter writes no timestamps, so the same input should give byte-identical `.glb` (verified by
running twice; result in the task report).

## 6. Effects on T22 / T20 / T28 plans (for the planner)

* **T22**: use cgltf directly as planned. Consider honouring `COLOR_0` (the viewer shader already
  multiplies `vertexColor`; raylib `Mesh::colors`); warn on primitives of 65 536 vertices or
  more (u16 truncation); the viewer shader samples no textures, so textured third-party models
  need a shader change. Compose full TRS per node even though ours are translation only. Wheels
  and rotors spin about a node-local axis, so the manifest should say which axis a part rotates
  about, or state a convention.
* **T20**: no change; `database.toml` for these models is written after T20 lands.
* **T28 (Unreal)**: `.glb` is importable. Check in a real import: pivot and hierarchy
  preservation, axis/scale conversion (glTF metres, +Y up, to Unreal centimetres, Z up), and
  whether the imported material uses `COLOR_0`. If pivots do not survive, USD is the fallback
  (the same Blender script can write it with `bpy.ops.wm.usd_export`).
